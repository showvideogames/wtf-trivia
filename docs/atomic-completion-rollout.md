# Atomic completion: backend preparation, not a release

Migration 0008 is unapplied to hosted databases. This draft adds two RPCs, coordinates existing mutation locks, and adds local database tests; it deliberately does not switch App.jsx to use them. Merging or deploying the frontend alone does not fix the remaining completion/stats consistency gap. Do not apply the migration without separate database/security release review.

## Existing failure and new contract

App.jsx currently completes game_records, reads player_stats, then upserts incremented counters. A lost response followed by retry can count one finish twice. A failure between writes leaves a completed game missing from totals. Two overlapping completions can overwrite each other's increments. A delayed older finish can overwrite the latest played date. PR77 fixes session/UI races, not these database consistency failures.

complete_my_game(_puzzle_id, _answers, _score) derives the owner from auth.uid(), locks that player's row, then locks their existing puzzle record. The first completed record wins; retry returns the same committed record rather than overwriting it. Completion, community trigger and canonical player stats recomputation share one transaction. A failure aborts all of them. A client must retry the same RPC after an uncertain response, use the returned record, and never fall back to the old incremental path after an RPC error.

my_reconciled_player_stats() takes the same player lock and rebuilds only the caller's stats from completed records. It returns null when there are none. It is a write RPC, not a read-only endpoint. Neither RPC accepts a player ID. Anonymous authenticated guests and signed-in accounts both own players via auth.uid(). Unauthenticated callers cannot execute either function. Existing grants, RLS, scoring trust and guest consent/merge rules remain unchanged; this is not an anti-cheat change.

Both RPCs reuse recompute_player_stats exactly: totals include every completed record, dates are distinct for streaks, best combo comes from answers, current streak ends at the most recent completed game date (not today). Legacy completed records remain unchanged even if their old answer payload is incomplete. Existing malformed date behavior is retained: a date that matches the baseline regex but cannot cast to date aborts recomputation and thus a new completion. Inspect such data only under a separately authorized release/data plan; no bulk repair is included.

## Compatibility boundary and rollout

1. Review migration, function privileges, local PostgreSQL test results and production schema drift before applying anything. No automatic deployment workflow applies this migration.
2. Apply only to the separately approved WTF backend, then verify function availability without creating live gameplay fixtures. Existing clients continue unchanged.
3. A separate frontend change must use the existing original-owner bound request for the completion RPC, publish returned stats only to the current UI owner, and use the reconciliation RPC on account/stat reload. It must preserve the synchronous Results transition and retry affordance from PR77. Gate that change off by default until schema availability is verified.
4. Mixed old clients still directly PATCH records and upsert cached counters. They do not take the new player lock, can overwrite completed records/counters, and are NOT covered by the atomic/idempotent guarantee. A new reconciliation repairs the aggregate from its sequence of Read Committed statement snapshots, but an old writer can corrupt it again afterwards. Import, account deletion, handoff creation and account refresh now take parent player locks before child rows. Import discovers the guest without locking, locks both players in UUID order, then locks and revalidates the one-time code. This prevents the previously demonstrated record/parent deadlocks while preserving explicit guest consent. Real PostgreSQL tests force completion/import/deletion contention and include baseline-function negative controls. Legacy direct writers still bypass this protocol; separate recomputation queries may observe differing Read Committed snapshots under those writes.
5. A strict cutover needs a separately reviewed strategy for retiring old clients, restricting direct completion/stats writes, and coordinating import. Do not revoke existing privileges in this preparation migration: that would break old clients. No claim of portfolio-wide or mixed-client atomicity is made.

Rollback before client adoption: leave the unused RPCs and coordinated existing functions installed; no data backfill occurred. Restoring older import/deletion/refresh definitions requires a separate review and must not coexist with active new completion callers, because it reintroduces the demonstrated lock inversions. After client adoption, disable the new client path first and revert code if needed; the old path's known consistency gaps return. Dropping the two functions is optional only after confirming no callers remain and obtaining database change approval. Never roll back by deleting completed games or overwriting totals from browser snapshots.

## Verification

`npm run db:start && npm run db:reset && npm run test:db:completion` uses the existing local Supabase/Docker harness. CI starts an ephemeral PostgreSQL 17 stack with fixture auth users; it needs no repository secrets or hosted connection. Tests cover retries, concurrent finishes, rollback on aggregate failure, ownership, guests/accounts, legacy streak semantics and reconciliation after legacy writes. Concurrent RPC tests exercise real PostgreSQL but do not prove arbitrary legacy/import interleavings safe.

The development Mac has no Docker, so these database tests cannot run there. CI results must be checked before approving this draft. Real hosted sign-in, token expiry during a retry, multiple browser/device flows and rollout remain unverified.

## Blocking historical-data preflight and compatibility decision

Do not adopt either new RPC until a separately authorized preflight checks (1) completed records whose ISO-shaped game_date is not a valid calendar date, (2) cached best_combo greater than the maximum recoverable best_combo from completed answer arrays, and (3) cached stats with no remaining completed records. Run no historical reconciliation as part of preflight. Current tests explicitly demonstrate all three baseline behaviors: an impossible date aborts new completion and leaves both prior stats and the unfinished game unchanged; incomplete answer history can lower best_combo; absent completed history deletes cached stats. These are unresolved adoption blockers, not an invitation to repair live rows.

Proposed policy for review: fail closed for affected owners, preserve existing records and cached stats, and expose a repair-needed result rather than silently replacing a historical best or deleting cached history. Decide separately whether to retain unverifiable historical counters or rebuild them from durable records, and how to quarantine invalid dates. This draft intentionally retains baseline recomputation semantics until that decision; it does not guess what the user's historical best should be. The rollout gate is closed until both that decision and coordinated old-client cutover are implemented and tested.
